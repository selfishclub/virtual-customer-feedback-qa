# 패널 구성 규칙

> 누구에게 물을지가 무엇을 물을지보다 먼저다.

---

## 1. 기본 패널 — 5인 구조

**핵심 사용자 2 + 경계 사용자 2 + 비사용자 1 = 5명.**
이 구조가 blind spot 발굴에 가장 효과적이었다. 특별한 이유가 없으면 이 구성을 쓴다.

| 자리 | 누구 | 선정 조건 | 무엇을 잡나 |
|---|---|---|---|
| **핵심 1** | 타깃 정중앙 | 타깃 조건 **전부 일치** | 정상 경로. "잘 되는 것" |
| **핵심 2** | 타깃 정중앙 (다른 성별·지역) | 타깃 조건 **전부 일치** | 핵심1의 반응이 개인차인지 확인 |
| **경계 1** | 타깃 언저리 | 조건 **1개만 어긋남** (나이 ±10 등) | 타깃을 넓힐 수 있는지 |
| **경계 2** | 타깃 언저리 (다른 축으로) | 조건 **1개만 어긋남** (지역·직군 등) | 타깃을 좁혀야 하는지 |
| **비사용자** | 명백히 밖 | 조건 **2개 이상 어긋남** | 약점. 무시해도 되는 거절과 아닌 거절 구분 |

**경계 사용자가 이 구조의 핵심이다.** 핵심만 부르면 다 좋다고 하고, 비사용자만 부르면 다 싫다고 한다.
**타깃의 진짜 경계선은 경계 사용자에게서 드러난다.**

## 모드별 예외

| 모드 | 인원 | 구성 |
|---|---|---|
| I1 패널 인터뷰 | **5명** | 기본 구조 |
| I2 5초 테스트 | **5명** | 기본 구조 |
| I3 비고객 스트레스 | **3명** | 비사용자만 3명 |
| I4 가격·혜택 | **4명** | 핵심 2 + 경계 2 (비사용자는 가격 판단이 무의미) |
| Q1 흐름 QA | **3명** | 핵심 1 + `#저디지털`/`#접근성` 1 + `#테크회의론`/`#약관정독` 1 |
| Q2 라이브 QA | **1~2명** | 한 번에 한 명씩. 실행 비용이 크다 |

## 2. 선정 절차

### 확장 팩(L2)이 있을 때

```
1. 타깃 조건을 항목으로 분해   → 나이대 / 성별 / 직업군 / 지역 / 태그
2. 쿼리 3발
   - 핵심 : 전 조건 AND        → 2명
   - 경계 : 조건 1개 완화       → 2명
   - 비사용 : 조건 반전         → 1명
3. 후보가 많으면 다양성 우선 (같은 직업·지역 중복 회피)
4. 후보가 없으면 조건을 한 단계씩 완화하고 그 사실을 보고
```

### 코어 팩(L1)만 있을 때

35명뿐이라 전 조건 일치가 거의 안 나온다. **근사치를 쓰되 반드시 격차를 명시한다.**

```
1. 태그로 1차 필터
2. 나이·직업·지역 순으로 가장 가까운 사람 선정
3. 각 페르소나 소개에 [격차] 한 줄 필수:
   "타깃과 다른 점 — 직업이 부동산 영업이 아니라 보험 상담입니다"
```

**절대 금지** — 페르소나에게 없는 직업·경험·취향을 씌우는 것.
그 순간 통계 근거가 사라지고 그냥 지어낸 인물이 된다. 스킬을 쓸 이유가 없어진다.

## 3. 패널 스냅샷 — 재현성 장치

쿼리로 매번 뽑으면 사람이 바뀌어서 **수정 전후 비교가 불가능하다.**
한 번 구성한 패널은 저장하고 재사용한다.

### 저장 형식

세션 종료 시 아래를 산출한다. 사용자가 파일로 보관하거나 다음 세션에 붙여넣는다.

```markdown
## 📌 패널 스냅샷 — (프로젝트명)
- 생성일: YYYY-MM-DD
- 타깃 정의: (한 줄)
- 소스: 코어팩(L1) / 확장팩(L2) / 전체(L3)

| 자리 | ID | 이름 | 나이·성별 | 직업 | 지역 | 태그 |
|---|---|---|---|---|---|---|
| 핵심1 | C1 | 김세원 | 34 남 | 스마트스토어 운영 | 안산 상록구 | #1인사업자 #고디지털 |
| 핵심2 | … | | | | | |
| 경계1 | … | | | | | |
| 경계2 | … | | | | | |
| 비사용 | … | | | | | |
```

### 재사용 규칙

- 같은 프로덕트를 다시 테스트하면 **반드시 같은 패널**을 쓴다
- 패널을 바꿔야 할 때는 **왜 바꾸는지 한 줄로 남긴다** (타깃이 바뀌었다 등)
- 패널이 바뀐 채로 전후 비교를 하지 않는다

## 4. 세그먼트 정의 (코어 팩)

세그먼트는 큰 서랍일 뿐이다. **정밀 선정은 태그로 한다.**

| 코드 | 세그먼트 | 인원 | 이런 타깃일 때 |
|---|---|---|---|
| **A** | 2030 싱글·직장인·취준 | 10 | 자기계발 · 생산성 · 사이드프로젝트 · 구독 |
| **B** | 3040 부모·가족 중심 | 6 | 육아 · 가족 소비 · 교육 · 살림 |
| **C** | 1인 사업자·자영업·전문직 | **5** ⚠️ | B2B 툴 · 마케팅 · 매출 · 커머스 |
| **D** | 4050 직장인·전문직 | 6 | 커리어 · 재테크 · 건강 |
| **E** | 5060+ 시니어·저디지털 | 8 | 시니어 서비스 · **비고객 테스트** · **온보딩 QA** |

> ⚠️ **C가 가장 얇다(5명).** 1인 사업자·프리랜서가 타깃이면 코어 팩만으로는 부족하다.
> 확장 팩을 만들고 `--balance custom --weights C=0.35` 처럼 해당 세그먼트를 두껍게 잡는다.

## 5. 타깃이 없을 때

사용자가 타깃을 안 정했으면 **후보를 열어주되 최종 선택은 사용자가 한다.**

```
이 프로덕트라면 이런 분들이 먼저 떠올라요:
① 30대 워킹맘 — 반찬 준비 시간이 가장 아쉬운 집단
② 자취 시작한 20대 직장인 — 요리 스킬·도구가 없음
③ 부모님 반찬을 챙기는 40대 자녀 — 구매자와 사용자가 다른 케이스

어느 쪽으로 갈까요? 다른 타깃이 있으면 그걸로 가도 됩니다.
```

**확인 없이 ①로 진행하지 않는다.** 타깃을 좁히는 판단 자체가 사용자의 몫이다.
스킬은 선택지를 여는 역할까지만 한다.
