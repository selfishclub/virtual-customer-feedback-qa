# QA 플레이북

> 페르소나가 **말로 평가하는 것**과 **실제로 해보다 막히는 것**은 다르다.
> 이 문서는 후자를 다룬다. 모드 Q1(흐름 QA)·Q2(라이브 QA)에서 반드시 읽는다.

---

## 1. 대원칙

1. **페르소나는 테스터가 아니라 생활인이다.** 버그를 찾으려 애쓰지 않는다. **자기 목적을 이루려다 막힌다.**
2. **막히면 거기서 멈춘다.** 억지로 완주시키지 않는다. 실제 사용자는 포기한다.
3. **"왜 막혔는지"를 사용자 언어로 적는다.** `버튼 대비 부족`이 아니라 **"글씨가 연해서 눌리는 건지 아닌지 몰랐어요."**
4. **되돌릴 수 없는 행동은 하지 않는다.** 실제 제출·결제·가입 완료·발송은 금지. 그 직전에서 멈추고 보고한다.
5. **페르소나 능력 밖의 일은 안 된다.** `#저디지털` 페르소나가 개발자 도구를 열지 않는다. 못 하는 채로 막히는 게 데이터다.

---

## 2. 막힘 6유형 (Blocker Taxonomy)

QA 리포트의 모든 막힘은 아래 여섯 중 하나로 분류한다. **분류가 곧 처방을 결정한다.**

| 코드 | 유형 | 정의 | 전형적 발화 | 처방 방향 |
|---|---|---|---|---|
| **B1** | **못 찾음** | 요소는 화면에 있는데 발견하지 못함 | "어디를 눌러야 되는 건지 모르겠는데요" | 위치·크기·대비·순서 |
| **B2** | **못 알아봄** | 봤지만 의미를 이해하지 못함 | "이게 무슨 말이에요? 온보딩이 뭔데요" | 용어·카피·설명 |
| **B3** | **못 믿음** | 이해했지만 신뢰가 안 서서 멈춤 | "여기다 전화번호를 왜 적어요" | 근거·보증·최소수집 |
| **B4** | **못 함** | 하려는데 조작이 실패함 | "눌렀는데 아무것도 안 되던데요" | 인터랙션·입력형식·반응성 |
| **B5** | **안 함** | 할 수 있고 이해도 했는데 **할 이유가 없음** | "할 수는 있는데… 굳이요?" | 가치제안·타이밍·유인 |
| **B6** | **끊김** | 기술적 실패 | 404 · 에러 · 무한 로딩 | 버그 수정 |

### B5가 이 스킬의 존재 이유다

일반 QA는 **"되는가"**를 본다. B1·B4·B6은 개발자도 잡는다.
**B5는 기능이 완벽해도 발생한다.** 다 되는데 아무도 안 누르는 상태 — 서비스를 만들고 가장 막막해지는 그 지점이다.
B5가 나왔으면 **리포트 최상단에 올린다.**

### 분류가 애매할 때

| 헷갈림 | 판정 기준 |
|---|---|
| B1 vs B2 | **눈이 못 찾았으면 B1, 눈은 찾았는데 머리가 못 따라갔으면 B2** |
| B2 vs B5 | **이해를 못 해서 멈췄으면 B2, 이해했는데 안 했으면 B5** |
| B3 vs B5 | **불안해서 멈췄으면 B3, 무덤덤하게 안 했으면 B5** |
| B4 vs B6 | **내 조작이 틀린 것 같으면 B4, 시스템이 깨진 것 같으면 B6** |

## 3. 심각도 3단계

| 등급 | 이름 | 정의 |
|---|---|---|
| **S1** | **이탈** | 여기서 나갔다. 다시 안 온다 |
| **S2** | **지연** | 헤맸지만 결국 통과했다 |
| **S3** | **잔여 불쾌** | 완료는 했는데 찜찜함이 남았다 |

**S1이 하나라도 있으면 그것부터 고친다.** S2 열 개보다 S1 하나가 비싸다.
S3을 무시하지 않는다 — 재방문·추천에서 조용히 깎인다.

## 4. 모드 Q1 — 흐름 QA (문서 기반)

**어디서든 된다.** 브라우저 접근이 없어도 실행 가능. 기본 QA 모드.

### 입력으로 받을 것

셋 중 하나면 시작한다.

- 단계 나열 (예: 링크 → 상세페이지 → 신청폼 → 완료)
- 스크린샷 (순서대로)
- 랜딩페이지 텍스트·카피 전문

**부족하면 한 번만 묻는다.** "첫 화면에 뭐가 보이는지 한 줄로 알려주세요" 정도.

### 패널

**3명.** 반드시 이 조합을 지킨다.

| 자리 | 누구 | 왜 |
|---|---|---|
| 1 | **타깃 핵심 사용자** | 정상 경로 확인 |
| 2 | **`#저디지털` 또는 `#접근성`** | 조작 한계 노출 |
| 3 | **`#테크회의론` 또는 `#약관정독`** | B3·B5를 가장 잘 잡음 |

### 진행

각 페르소나가 **단계마다** 아래 넷 중 하나로 반응한다.

```
통과   — "다음 눌렀어요"
머뭇   — "여기서 잠깐 헷갈렸는데…" + 이유
막힘   — "여기서 멈췄어요" + 이유 (계속은 함)
이탈   — "여기서 껐어요" + 이유 (★ 여기서 그 페르소나 종료)
```

**이탈하면 그 페르소나의 워크스루는 끝이다.** 나머지 단계를 상상해서 채우지 않는다.

### 반드시 물어야 할 3+1

각 단계에서 페르소나가 스스로 답한다.

1. **지금 뭘 하라는 화면인가요?** → B2 감지
2. **다음에 뭘 눌러야 하나요?** → B1 감지
3. **하고 싶으세요?** → **B5 감지** ★
4. (개인정보·결제 단계에서만) **여기다 이걸 적어도 괜찮으세요?** → B3 감지

## 5. 모드 Q2 — 라이브 QA (실제 브라우저)

**Cowork 또는 Claude Code에서 브라우저 도구가 있을 때만.** 없으면 Q1으로 폴백한다.

### 안전 규칙 — 먼저 읽는다

| 해도 되는 것 | **절대 안 되는 것** |
|---|---|
| 페이지 열기 · 읽기 | **폼 최종 제출** |
| 스크롤 · 클릭(이동) | **결제 · 구매** |
| 스크린샷 | **회원가입 완료** |
| 입력칸에 **테스트값 타이핑** | **메일·알림 발송** |
| | **삭제 · 취소 버튼** |

> **되돌릴 수 없는 행동 직전에서 멈춘다.** 제출 버튼 앞까지 가서 "여기서 멈췄습니다. 실제 제출은 하지 않았어요"로 보고한다.
> 실제 서비스에 테스트 데이터를 남기지 않는 것이 원칙이다.

### 진행

```
1. 사용자에게 URL과 목표 행동을 받는다 ("신청 완료까지")
2. 페르소나 1명을 정한다 (한 번에 한 명. 섞지 않는다)
3. 페이지를 연다 → 스크린샷
4. 그 페르소나의 눈으로 판정한다:
   - 지금 보이는 것 중 이 사람이 실제로 읽을 것은?
   - 이 사람의 디지털 숙련도로 다음 행동을 찾을 수 있나?
5. 행동 → 스크린샷 → 4로 반복
6. 이탈하거나 목표 직전에 도달하면 종료
```

### 페르소나 눈으로 본다는 것

같은 화면도 사람마다 다르게 읽힌다. 판정 시 반드시 반영한다.

| 태그 | 어떻게 다르게 보나 |
|---|---|
| `#저디지털` | 화면 상단만 본다. 스크롤을 잘 안 한다. 아이콘만 있는 버튼은 못 알아본다 |
| `#접근성` | 작은 글씨를 못 읽는다. 연한 회색 텍스트는 없는 것과 같다 |
| `#보안민감` | 입력 필드를 보면 "이걸 왜 받지"부터 생각한다. 개인정보 처리방침 링크를 찾는다 |
| `#약관정독` | 실제로 약관을 연다. 없거나 깨져 있으면 그 자체가 막힘이다 |
| `#테크회의론` | 새 개념이 나오면 "기존 방식 대비 뭐가 나은지"를 먼저 따진다 |
| `#고디지털` | 빠르게 훑고 지나간다. 대신 **어색한 지점을 정확히 짚는다** |

### 기록할 것

각 단계마다 남긴다.

- 어느 화면 (URL 또는 스크린샷 번호)
- 무엇을 하려 했나
- 무슨 일이 벌어졌나
- **막혔다면 → 유형(B1~B6) + 심각도(S1~S3)**

## 6. QA 리포트 양식 (Q1·Q2 공통)

세션이 끝나면 이 형식으로 산출한다. **표 → 상세 → 우선순위** 순서를 지킨다.

```markdown
## 🧪 QA 리포트 — (프로덕트명)

**대상**: (URL 또는 흐름 이름)
**패널**: (이름 · 나이 · 직업 · 태그) × N
**방식**: Q1 문서 기반 / Q2 실제 브라우저
**날짜**: YYYY-MM-DD

### 단계별 통과 현황

| 단계 | 페르소나1 | 페르소나2 | 페르소나3 |
|---|:---:|:---:|:---:|
| 1. 랜딩 진입 | 통과 | 머뭇 | 통과 |
| 2. 내용 이해 | 통과 | **이탈 B2/S1** | 머뭇 |
| 3. 신청 버튼 | 머뭇 | — | **이탈 B5/S1** |
| 4. 폼 입력 | **막힘 B3/S2** | — | — |

*— 는 이미 이탈해서 도달하지 못함*

### 막힘 상세

| # | 유형 | 심각도 | 어디서 | 누가 | 그 사람 말 | 처방 |
|---|---|---|---|---|---|---|
| 1 | **B5** | **S1** | 신청 버튼 | 김남희(53·네트워크 전문가) | "할 수는 있는데, 지금 해야 할 이유를 모르겠어요" | 마감·혜택을 버튼 옆에 |
| 2 | B2 | S1 | 히어로 카피 | 전기태(74·하역) | "온보딩이 뭐요?" | 용어 풀어쓰기 |
| 3 | B3 | S2 | 폼 | 송순근(49·보안) | "전화번호는 왜 필요한데요" | 수집 이유 명시 / 선택항목화 |

### 먼저 고칠 것 3개

1. **(S1)** …
2. **(S1)** …
3. **(S2)** …

### 이번 QA가 확인하지 못한 것

- (실제 결제 흐름 — 안전 규칙상 미진행)
- (모바일 화면 — 데스크톱만 확인)
- (실제 고객의 반응 — 가상 QA는 실제 검증을 대체하지 않음)
```

## 6-2. 잘 된 것도 기록한다

**막힘만 적으면 리포트가 자동으로 부정 쪽으로 기운다.** 통과한 단계마다 한 줄씩 남긴다.

| 무엇 | 어떻게 |
|---|---|
| **왜 쉬웠나** | "버튼이 화면 한가운데 크게 있어서 바로 눌렀어요" |
| **어떤 표현이 통했나** | "'3분이면 끝나요'가 있어서 시작했어요" |
| **어떤 신뢰 근거가 먹혔나** | "후기가 밑에 바로 보여서 의심이 덜했어요" |

이건 **다음에 고칠 때 건드리면 안 되는 부분**을 표시하는 일이다.
개선한다고 손댔다가 잘 되던 걸 망가뜨리는 사고가 여기서 막힌다.

리포트 단계별 표에서 통과 칸에 짧은 이유를 함께 적는다.

```
| 1. 랜딩 진입 | 통과 (버튼이 큼) | 머뭇 | 통과 |
```

## 7. 흔한 실수

| 실수 | 왜 문제인가 |
|---|---|
| 페르소나가 버그를 "찾으러" 다님 | 실제 사용자는 버그를 찾지 않는다. 자기 목적만 본다 |
| 이탈한 페르소나를 계속 진행시킴 | 그 뒤 데이터는 전부 허구다 |
| 막힘을 전부 B1로 분류 | 처방이 "버튼 키우기"로만 수렴한다. 6유형을 실제로 구분할 것 |
| B5를 리포트에서 뺌 | 가장 비싼 문제를 빠뜨리는 것 |
| 개선안까지 페르소나가 말함 | 고객은 해결책을 모른다. **증상은 페르소나가, 처방은 리포트가** |
| 실제 폼을 제출함 | 안전 규칙 위반. 남의 서비스에 쓰레기 데이터를 남긴다 |
| **막힘만 적고 통과는 안 적음** | 리포트가 부정 편향된다. 유지할 부분을 모르게 된다 |
| 전원이 이탈함 | 정말 그런지, 아니면 페르소나를 부정적으로 몰았는지 다시 본다 |
